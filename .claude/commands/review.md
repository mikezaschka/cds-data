# Review

Read-only audit of a diff or PR against the project's cross-document invariants. **No code or doc changes are written by this command** — it emits a checklist report. Fixes happen via `/implement-feature`, `/fix-bug`, `/update-requirements`, `/discuss-architecture`, or `/deprecate`.

**Input:** a git range. Default: `origin/main...HEAD`. Caller may pass an explicit range (e.g. `HEAD~3...HEAD`) or a PR number.

**Output:** a structured report with one section per check, each marked `PASS`, `FAIL`, or `N/A (why)`.

## Phase 1 — Collect the diff

1. `git diff --stat <range>` and `git diff <range>` — the mechanical change set.
2. `git log <range> --oneline` — commit messages (for conventional-commit + scope hygiene).
3. Categorize the touched paths:
   - `lib/**`, `srv/**`, `packages/*/srv/**` — plugin runtime code
   - `test/**` — test changes
   - `spec/reference/requirements.md` — contract
   - `spec/concepts/**` — contributor canonical concept source
   - `docs/pipeline/** and docs/federation/**` — published per-package documentation sites
   - `packages/*/README.md` — per-package READMEs shipped to npm
   - `spec/internal/**` — internal reference, decisions, research, ideas
   - `examples/**` — example apps and `.http` files
   - `README.md`, `CLAUDE.md`, `AGENTS.md`, `.cursor/rules/**` — entry points

The checks below only run for categories touched by the diff.

## Phase 2 — Invariants

### Req-1: Every behavioral code change is traceable to a requirement ID

- Every new or modified `it(...)` in `test/**` starts with `[<id>]` or an explicit `[N/A]` (pure infrastructure tests only).
- Every new behavior in `lib/**` or `srv/**` lands with at least one test whose `[<id>]` matches a row in `spec/reference/requirements.md`.
- Search the diff for added `it(` lines and check each one.

### Req-2: Requirements contract is in sync

- If `lib/**` or `srv/**` changed, did a row in `spec/reference/requirements.md` move status (e.g., `Not started → In progress → Implemented`)? If not, flag it.
- Run `npm run sync:requirements` mentally: does the Progress Summary match the section tables? The script is idempotent — if the diff changed status cells but not the summary, that's a FAIL.
- `spec/reference/test-mapping.md` is regenerated by the same script; it must not be stale.

### Req-3: Scenario names are canonical

- Any occurrence of old scenario labels (`Scenario A`, `Scenario B`, `Scenario C`, `N1`/`N2` as the primary identifier, `Scenario N`) in the diff → FAIL unless it is (a) inside a historical ADR or research note, or (b) followed by the canonical name in parentheses.
- Canonical set lives in [`spec/concepts/cross-service-scenarios.md`](../../spec/concepts/cross-service-scenarios.md). Names: `Delegated expand`, `Cross-service expand: local → remote`, `Cross-service expand: remote → local`, `Cross-service expand: cross-provider`, `Cross-service navigation: local → remote`, `Cross-service navigation: remote → local`.

### Req-4: Entry points stay thin

- `CLAUDE.md`, `AGENTS.md`, `.cursor/rules/project.mdc` must remain pointers. Any diff that adds substantive architecture, lifecycle, or CDS-quirk content to them is a FAIL — that content belongs in `spec/internal/ai-assistant-context.md` or `spec/concepts/**`.
- Heuristic: net additions > ~30 lines to any of these three files warrants a manual re-read.

### Req-5: Low-redundancy rule

External (`spec/concepts/**`, `README.md`, `examples/**`) and internal (`spec/internal/**`) docs are allowed to repeat each other where the audiences differ. Everything else must not.

- No two files in the diff introduce the same paragraph of prose. If paragraph X is added to file A and file B, one of them should be a link instead.
- ADRs (`spec/internal/decisions/**`) must not restate requirement text — they link to the requirement ID.
- Ideas (`spec/internal/ideas/**`) must not restate ADR content — they link.

### Req-6: Removed-status hygiene

If any row in `spec/reference/requirements.md` moved to `Removed (…)`:

- There is a matching ADR in `spec/internal/decisions/` explaining why.
- `README.md` and `examples/**` no longer advertise the feature.
- Tests tagged with the requirement ID are either deleted or explicitly marked `[N/A — removed, see ADR NNNN]`.

See [`/deprecate`](./deprecate.md) for the full workflow.

### Req-7: Examples stay executable

- If `lib/**`/`srv/**` annotations or CSN shape changed, re-check `examples/consumer/srv/**` and any `.http` files for stale literals.
- `examples/consumer/package.json` → `npm test` must still pass. Call this out if not verified.

### Req-8: Conventional commits + scope

- Commit subjects match `feat:`, `fix:`, `chore:`, `docs:`, `test:`, `refactor:` (or scoped variants).
- A single commit does not mix a feature change with an unrelated refactor. Suggest a split if it does.

### Req-9: MCP-introspectable changes use MCP

When the diff touches CDS models, annotations, or OData endpoints, `cap-mcp` and `fiori-mcp` should have been consulted rather than grep-guessing. Not enforceable mechanically — note as an advisory check only.

### Req-10: External docs tone

Only runs when the diff touches files in the published scope. Published scope per [`spec/internal/docs-style-guide.md`](../../spec/internal/docs-style-guide.md) §Scope:

- `docs/**/*.md` excluding `spec/internal/**`, `spec/concepts/**`, `spec/reference/requirements.md`, `spec/reference/test-mapping.md`
- `docs/pipeline/** and docs/federation/**/*.md` — per-package site pages
- `packages/*/README.md` — per-package npm READMEs
- `README.md` — root README, **except its `## For contributors` section** (the single permitted home for R5 exceptions)
- `examples/**/README.md`

The five rules (R1 tutorial voice, R2 no adversarial library comparisons, R3 no status/priority/roadmap content, R4 no rhetorical-contrast vocabulary, R5 no internal references on published surfaces) are documented in the style guide.

**Mechanical check for R4** — the grep below should return nothing on the diff's added lines (and ideally on the whole published surface after the change):

```bash
grep -rnE 'stops short|hand-written|boilerplate|does not do|despite the name|what .* does NOT' \
  docs/ README.md packages/*/README.md examples/ \
  --include='*.md' --exclude-dir=internal 2>/dev/null
```

**Mechanical check for R5** — the grep below should return only lines inside the root `README.md` `## For contributors` section. Hits anywhere else are a FAIL.

```bash
grep -rnE 'spec/internal/|ADR 00[0-9]+|ADR-00[0-9]+|\[ADR [0-9]+\]|CLAUDE\.md|AGENTS\.md|reference/requirements\.md|reference/test-mapping\.md' \
  README.md packages/*/README.md examples/ \
  --include='*.md' 2>/dev/null
```

When reading R5 hits from the root `README.md`, locate the `## For contributors` heading and treat everything beneath it as PASS; everything above it must be clean.

Any R4 hit or R5 hit outside the permitted scope is a `FAIL` with a suggested rephrasing. R1–R3 are reviewer judgment — flag pages that read as benchmark-style comparison or that surface `Priority` / `Phase` / `Status` / requirement IDs to consumers. Opinion paragraphs belong under `spec/internal/research/` and can be linked from published pages via an absolute GitHub URL.

## Phase 3 — Report format

```
## Review: <range>

### Summary
<N> checks run, <P> pass, <F> fail, <S> skipped.

### Req-1 Test traceability — PASS | FAIL | N/A
- <detail per finding, with file:line and suggested fix>

### Req-2 Requirements sync — ...
...
```

End the report with a **Suggested next command** line pointing at the right follow-up workflow (`/update-requirements`, `/fix-bug`, `/deprecate`, etc.) when any check failed.

## Non-goals

- This command does not run tests. It reads the diff and the repository; it does not exercise code. If the caller wants a green-CI check, they should run `npm test` themselves.
- This command does not write files. It is review, not repair.
